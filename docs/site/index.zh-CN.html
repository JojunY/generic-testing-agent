01 — 问题

绿了，不等于对了。

一个模型既写测试、又判断测试对不对，就会把测试一直改到变绿为止。借贷示例里的一个方法就足以说明：库存服务没有应答时，降级方法却说股份已经预留：

// InventoryClient.java
Reservation inventoryDown(String security, long quantity, Throwable cause) {
    return new Reservation(true);
}

模型给自己打分

它断言的是代码现在的行为。

它读了这个方法，写出一个期望“借券成功”的测试，运行，然后报告成功。

assertThat(response).hasStatus(201);
期望值 201BOOKED 通过

绿了。而这个缺陷从此有了一个保护它的测试。

示意：对这个方法“自己打分”的测试会是什么样。

gta

它断言的是人签过字的期望。

analyst 发现 docs/business-rules.md 与代码不一致，于是提问。人对推荐答案回复 OK。gtaw 运行测试，得到 expected: 503 but was: 201，重跑确认，交给 reviewer 分流，然后再问一次人。

assertThat(response).hasStatus(503);
锁定值 503PENDING_LOCATE 缺陷已标注

构建保持绿色，缺陷始终可见。

真实录制：下方可以重放这次运行。

02 — 核心想法

三方，各司其职。

银行把这叫做经办与复核：录入的人，永远不是批准的人。gta 把这条规矩用在测试上。

Agent

写

analyst · test author · reviewer

  • 阅读代码
  • 编写规格，附带问题和推荐答案
  • 每份 brief 写一个测试
  • 对测试或失败给出意见

绝不

  • 判定测试通过
  • 修改状态或提交
  • 改动生产代码

gtaw

判

一个 Java 命令行程序 · 内部没有模型

  • 根据已批准的规格排出条目
  • 运行测试
  • 检查规格里的期望值确实被断言，并将其锁定
  • 还原条目范围之外的改动
  • 提交，并执行质量门禁

绝不

  • 猜测：它判断不了的，交给人

你

签

开发者 · 产品负责人

  • 回答问题，通常一句 OK
  • 批准规格
  • 确认缺陷

不必

  • 逐个阅读测试：你签的是规格

05 — 边界

它不会去的地方。

  • SIT不提供服务
  • UAT不提供服务
  • PROD不提供服务
  • 不碰已部署的环境。测试只在开发机或 CI 上运行，依赖用内嵌或假的实现。没有任何模式会指向 SIT、UAT 或生产环境。
  • 不借用你的身份。gtaw 每次运行测试都会切断云凭据，并移除你的 Spring profile：即使终端指向 UAT，测试也不会加载 UAT 的配置。
  • 不改生产代码。条目范围之外的改动会被还原。缺陷只会被标注并上报，绝不会被悄悄修掉。

目前的状态

已验证

裁判。gtaw 有单元测试（行覆盖率门槛 90 %）和六套脚本化的端到端运行，其中由脚本扮演 agent。四个示例服务里预埋的 21 个缺陷全部被发现并标注。

尚未验证

选手。本仓库还没有用真实模型在真实服务上运行的记录。在各项能力完成试点之前，请都视为“尚未用模型验证”。

下一步

在一个真实服务上做试点；要记录什么、由什么决定结果，都有清单：试点指南。

06 — 开始

一个脚本，然后/gta。

脚本会构建一次 gta，把它安装到你的服务里（wrapper 固定指向这个 jar），并运行 ./gtaw doctor。之后用 VS Code、IntelliJ 或 OpenCode 打开你的服务。
