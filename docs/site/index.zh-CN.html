通用测试 agent · Java / Spring

测试可以交给 agent 写。通过与否，只有 gtaw 能判。

gta 是面向 Java / Spring 服务的测试 harness：先确认行为规格，再写测试。它运行在 GitHub Copilot 或 OpenCode 里。四个 agent 起草规格和测试。gtaw 是一个确定性的 Java 程序，它锁定你确认过的期望值、运行每一次测试，并且是唯一可以判定测试通过的一方。

01

常见的失败

让 agent 把失败的测试改成通过，它真的会去做。

通常是改测试本身。构建变绿，缺陷照样上线，没有人知道。gta 不把这一步交给 agent。

没有 gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • agent 改掉了期望值
  • ✓ 1 个测试通过 · 构建是绿的
缺陷上线了。没有人知道。
有 gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • ✗ gtaw：POLICY_ORACLE_MODIFIED，修改被拒绝
  • 重跑两次，结果相同，不是不稳定
  • → 作为缺陷报告，并用 @KnownDefect 标注
缺陷被抓住了。接下来怎么处理，由人决定。

期望值来自人确认过的规格，不来自代码今天的返回值。2024 年一项关于 LLM 生成 oracle 的研究发现，它们大多只是复述代码的实际行为（Konstantinou 等，arXiv:2410.21136）。这是这套设计的原因之一，不是在 gta 上测出来的成绩。

02

循环

一条命令。四个 agent。一个裁判。

输入 /gta 之后，orchestrator 向 gtaw 要下一个节点，再交给一个 agent。agent 读代码、写东西。gtaw 运行每一次测试，并做出 agent 可能判错的每一个决定。下面是 order.create 的编排回放，用的是 gtaw 真实消息的结构。

order-service · 编排回放
OATR 0/16
聊天 · /gta
给 gta 发消息…

          
终端 · gtaw

        

      

      
编排回放。四个名字是 gta-orchestrator、gta-analyst、gta-test-author 和 gta-reviewer。gtaw 没有标记，因为它不猜测。

      
回放需要 JavaScript。上面四步就是整个循环：读、问、锁、抓住。

    

  


  

    

      

        —
        

          
角色

          
四个 agent 各做一件事。记分的是一个程序。

          
权限就是围栏。写测试的 agent 不能宣布测试通过，也不能改生产代码。

        

      

      

        

          
你对话的那一个

          
gta-orchestrator

          
接收 /gta，向 gtaw 要下一个节点，再交给 analyst、author 或 reviewer。把 gtaw 的状态区块原样给你，英文或中文。它自己不写规格、不写测试，也绝不替你回答。

          
可以运行 gtaw 的 next、check、submit、answer、note、status。不能改文件、不能运行 git、不能判定测试通过。

        

        

          
读代码

          
gta-analyst

          
把一个 flow 写成行为规格：EARS 需求、场景、一张图，以及每一处不确定的问题。它描述，不判定今天的行为就是对的。

          
只能写 brief 指定的那份规格。不能自己写 source=confirmed。这个标记属于你，由 gtaw 记录。

        

        

          
写一个测试

          
gta-test-author

          
为一个已批准的场景写测试。期望值来自规格。规格和代码都定不了怎么写时，它问你，而不是猜。

          
只能改 brief 点名的测试文件。不能碰 src/main，不能削弱已锁定的断言，也不能把测试跳过。

        

        

          
判断，但不改文件

          
gta-reviewer

          
对照已批准的场景读测试。失败时给出一个判定：产品缺陷、测试缺陷、规格错误，或 brief 允许的其他原因。它不会建议把期望值改成代码实际返回的值。

          
只读。回一行：判定，以及理由。

        

      

      

        

          
裁判 · 不是 agent

          
gtaw

          
一个确定性的 Java 程序。同样的输入，同样的决定。它在这页上没有标记，因为它不猜测，也不调用模型。

        

        
    
          
  • 运行每一次测试，并重跑失败以排除不稳定
    • 
          
  • 锁定来自已批准规格的期望值
    • 
          
  • 还原agent 被允许修改的文件之外的改动
    • 
          
  • 提交走它自己的记录，所以旁路提交会被看见
    • 
          
  • 判定什么算通过。只有 gtaw 能这么说。
    • 
        

      

    

  


  

    

      

        03
        

          
七条捷径

          
试着作弊。gtaw 不会让你得逞。

          
你是测试作者。测试失败了：代码返回 0.00，已确认的规格写的是 10.00。选一条捷径。author 会去做，gtaw 用它真正会返回的拒绝来回答。这块板是编排的。同样的攻击会在 evals/e2e/run-adversarial.sh 里对 gtaw 真的执行一遍。

        

      

      

        

          
0/7条捷径被拦下

          

            
            
            
            
            
            
            
          

        

        

          

            

            

            

          

          
7 条全部被拦下，没有一条进入提交。这些攻击，再加上一条——同一事项的第三次尝试会停下来等人——会在 gta 的每次改动时于 CI 中重跑：evals/e2e/run-adversarial.sh。

          
这块板需要 JavaScript。这七种修改对应的拒绝是 POLICY_ORACLE_MODIFIED、POLICY_ORACLE_MISMATCH、POLICY_TEST_SKIPPED 和 POLICY_OUT_OF_SCOPE_CHANGE。上面的脚本会真的跑它们。

        

      

    

  


  

    

      

        04
        

          
边界

          
它会做什么，不会做什么。

          
下面是程序的性质，不是对一个我们没见过的部署环境作的承诺。

        

      

      

        

          
运行留在本机

          
测试在你的机器上跑。每次运行都会去掉云凭证，以及 shell 里的 Spring profile 和配置变量，所以一次 gta 运行不会加载 SIT、UAT 或生产配置。已部署的环境不在范围内。agent 的规则也只允许本地依赖。

        

        

          
不需要容器

          
Kafka 和 JMS 内嵌运行。BigQuery 和 GCS 用替身。Oracle 用 Oracle 模式的 H2，或一套共享的测试 schema。Pub/Sub 用内存替身，或从 Nexus 下载的模拟器。

        

        

          
测试必须能够失败

          
对单元测试和 slice 测试，gtaw 可以用 PIT 变异规格引用的方法；测试仍然通过就会被退回。PIT 跑不起来时只作报告，不据此判这个测试失败。质量门禁里的 mutation 默认是 advisory。

        

        

          
它问，不猜

          
每个问题都带一个推荐答案和理由。单独一个 OK 才接受推荐。OK, but … 不算。

        

        

          
你的原话就是记录

          
回答和批准按你写的原话保存，并带上修订号。以后的人能看到是谁确认了什么。

        

        

          
中文或英文

          
把 output.language 设为 zh-CN，问题和状态区块就用中文。OK、好、确认 都算 OK。

        06
        

          
你输入什么

          
八种入口。回来的是同一块状态。

          
gta 停下来等你时，那一块是 gtaw 写的：状态、发生了什么、检查了什么、需要你做什么、下一步是什么。orchestrator 不会再写一份自己的摘要。

        

      

      

        
你输入会发生什么

        
          
/gta继续，或列出 flow。回复 OK 会从风险最高的开始，把它们都做一遍。

          
/gta order.create规格、问题、你的批准，然后是这个 flow 的测试。

          
/gta explain order.create只写规格和问题，不写测试。

          
/gta service服务里的每一个 flow。一个在等你时，不会挡住其他的。

          
/gta pr …这条分支改到的 flow。PR 描述被当作意图。

          
/gta incident order.create …一份缺陷报告变成一个在今天的代码上失败的测试。再由你确认缺陷。

          
/gta note …代码里看不出来的事。记在 .gta/notes.md。

          
/gta statusflow、事项，以及正在等你的东西。

        
      

      
单独一个 OK 接受推荐。OK, 2B 改掉其中一个选项。好 和 确认 就是 OK。批准 order.create@R2 批准那一版。其余默认 对其余普通问题保留代码今天的行为。那些场景会变成特征测试：它们锁定代码现在做什么，并不证明这样做是对的。

安装

          
构建一次。之后的命令是 /gta。

          
在本仓库里，jar 就是你刚刚构建出来的那一个。已发布的 jar 还需要 --distribution-url 和 --distribution-sha256。gtaw 不会下载一个没有锁定校验的 jar。完整说明在快速上手。

        

      

      
    
        
  1. 
          
    
            mvn -B install
            
    在本仓库中执行。构建 gtaw 并运行它的测试。
    
          
    
          
        
    2. 
        
  2. 
          
    
            java -jar toolkit/gta-cli/target/gta-cli.jar --root my-service init --platform copilot
            
    每个服务做一次，通常由负责构建的人来做。OpenCode 用 --platform opencode，然后提交 init 写下的文件。从 Nexus 来的 jar 要按快速上手补上 URL 和 sha256。本地开发时，用 GTA_CLI_JAR 指向你构建出的 jar。
    
          
    
          
        
    3. 
        
  3. 
          
    
            cd my-service && ./gtaw doctor
            
    检查 JDK、构建和 harness。Windows 上用 .\gtaw.cmd doctor。
    
          
    
          
        
    4. 
        
  4. 
          
    
            /gta
            
    在服务里的 Copilot 聊天或 OpenCode 中输入。回复 OK 接受推荐，再批准它给你看的那一版规格。

        09
        

          
问题

          
第一次接触？从这里开始。

        

      

      

        
它会碰到生产环境吗？
它不测试已部署的环境。每次运行都会去掉云凭证，以及 shell 里的 Spring profile 和配置变量，agent 的规则也只允许本地依赖。SIT、UAT 和生产环境都不在范围内。

        
需要 Docker，或者另外的模型密钥吗？
gtaw 不需要。依赖以内嵌、替身，或（对 Pub/Sub）模拟器的方式运行。agent 使用你的 Copilot 或 OpenCode 已经提供的模型。gtaw 本身不调用模型。

        
它拿不准的时候怎么办？
它会问。问题里有它推荐的答案和理由，所以经常一个 OK 就够。代码里看不出来的事，可以用 /gta note 记一次。

        
什么是已知缺陷？
因为代码写错而失败的测试，用 @KnownDefect 标住。构建保持绿灯，缺陷仍然可见。代码修好之后，这个测试会一直失败，直到去掉标记。

        
目标是覆盖率吗？
不是。覆盖率只作参考。gta 检查的是：每个批准的场景有没有测试，单元或 slice 测试能不能失败，以及新测试是否稳定。

        
支持哪些 Java 和 Spring 版本？
Spring Boot 2.2 到 4.1。服务可以是 Java 8 及以上。Maven 或 Gradle，单模块或多模块，Windows、macOS 和 Linux 都可以。gtaw 本身需要 JDK 17 或更新。
