问题在哪

让 AI 把失败的测试改成通过，它真的会做到。

通常的做法是改测试本身。构建变绿，缺陷照样上线，没有人知道。gta 让这一招失效。

没有 gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • agent 把期望值改掉了
  • ✓ 1 个测试通过 · 构建变绿
缺陷上线了。没有人被告知。
有 gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • ✗ gtaw：POLICY_ORACLE_MODIFIED，改动被拒绝
  • 重跑 2 次，结果一致，不是不稳定
  • → 报告为缺陷，用 @KnownDefect 标记
缺陷被抓住了。接下来怎么做，由人决定。
工作方式

一条命令，四个 agent，一个裁判。

输入 /gta，看它们接力。agent 负责读代码、写测试；gtaw 是一个普通程序，负责跑每一个测试，并做出所有 AI 可能出错的判断。

团队

      
四个 agent 干活，一个程序记分。

      
每个 agent 只有一项工作，并且有明确的边界。记分的那一方，任何话术都说服不了它。

      

        
和你对话的那位
gta-orchestrator
接收你的 /gta，把每项工作交给合适的 agent，把每个结果交给 gtaw。给你看的只有一个状态区块，中英文都可以。
可以：和你对话、调用 gtaw

        
读代码
gta-analyst
把一个 flow 写成带图的行为规格，每条结论都注明出处。代码看不出的地方，它会问。
可以：写规格

        
写测试
gta-test-author
按批准的规格，每份任务书写一个测试。拿不准的时候，它会问，而不是猜。
可以：写自己的测试文件

        
评判结果
gta-reviewer
检查断言是否与规格一致，并评判每一次失败：产品缺陷、测试缺陷，还是规格写错。
可以：只读，别的都不行

      

      

        

          
裁判 · 不是 AI

          
gtaw

          
一个确定性的 Java 程序。输入相同，判定就相同，每一次都一样。它在这个页面上没有光标，因为它从不猜测。

        

        
    
          
  • 运行每一个测试，失败时重跑，排除不稳定
    • 
          
  • 锁定来自已批准规格的期望值
    • 
          
  • 还原任何超出 agent 自身文件范围的改动
    • 
          
  • 提交每一处改动都由它亲自提交，历史可信
    • 
          
  • 判定什么算通过。只有 gtaw 说了算。

值得信任

      
今天就可以放心用在真实的服务上。

      

        
生产环境不会被碰到
测试只在本地运行。每次运行都会去掉你 shell 里的 Spring profile 和云凭证，SIT、UAT 和生产环境都碰不到。

        
不需要容器
Kafka 和 JMS 内嵌运行，BigQuery 和 GCS 用 fake，Oracle 用 Oracle 模式的 H2 或共享的测试 schema。

        
测试必须会失败
变异测试会故意把代码改错，检查测试能不能发现。不管怎样都通过的测试会被退回。

        
只问，不猜
每个问题都附推荐答案和理由。大多数时候，你只需要回复 OK。

        
你的原话就是记录
回答和批准都写进规格和提交记录，审查的人能看到谁在什么时候决定了什么。

        
中文或英文
把 output.language 设为 zh-CN，所有问题和状态区块都用中文。OK、好、确认 这样的回复都能识别。

开始使用

      
装一次，之后只要一条命令。

      

        
1
java -jar gta-cli.jar --root my-service init --platform copilot
每个服务做一次，通常由 tech lead 完成。用 OpenCode 就改成 --platform opencode，然后提交。

        
2
./gtaw doctor
检查 Java、构建和测试环境。Windows 上用 .\gtaw.cmd doctor。

        
3
/gta
在聊天里输入。gta 列出服务里的 flow，风险高的在前。回复 OK 就全部覆盖。

        
4
OK
回答问题、批准规格、审查提交。测试和缺陷都会带着推荐答案回来找你。

常见问题

      
第一次接触？从这里开始。

      

        
它会碰到生产环境吗？
不会。gta 只在你的机器上运行测试。每次运行都会去掉你 shell 里的 Spring profile 和云凭证，agent 的规则也只允许使用本地依赖。已部署的环境，包括 SIT 和 UAT，都不在范围内。

        
需要 Docker 或 API key 吗？
都不需要。依赖以内嵌或 fake 的方式运行。agent 使用你的 Copilot 或 OpenCode 本来就提供的模型；gtaw 本身是一个本地 Java 程序，不调用任何 AI。

        
gta 拿不准的时候怎么办？
它会问你。每个问题都附上它推荐的答案和理由，通常回复一个 OK 就够了。agent 无法知道的事情，你可以用 /gta note 告诉它们一次。

        
什么是已知缺陷？
因为代码写错而失败的测试。gta 用 @KnownDefect 标记它：构建保持绿灯，缺陷被报告出来。等有人修好代码，这个测试会一直失败，直到去掉标记为止，所以不会被遗忘。

        
它只是在追覆盖率吗？
不是。覆盖率只作参考。gta 检查的是：每个批准的场景是否被验证，测试是否会失败（变异测试），以及测试是否稳定。

        
支持哪些 Java 和 Spring 版本？
Spring Boot 2.2 到 4.1，服务可以是 Java 8 及以上，Maven 或 Gradle，单模块或多模块，Windows、macOS 和 Linux 都可以。gtaw 本身需要 JDK 17+。
