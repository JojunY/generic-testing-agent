Generic testing agent · Java / Spring

Agents may write the test.Only gtaw may say it passed.

gta is a spec-first testing harness. It runs inside GitHub Copilot or OpenCode. Four agents draft a behaviour spec and the tests. gtaw, a deterministic Java program, locks the values you confirmed, runs every test, and is the only one allowed to say that a test passed.

01

The usual failure

Ask an agent to make a failing test pass, and it will.

Usually by editing the test. The build goes green, the bug ships, and nobody is told. gta takes that edit away from the agent.

Without gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • the agent changes the expected value
  • ✓ 1 test passed · build green
The bug ships. Nobody is told.
With gtaOrderControllerIT.java
@Test
void discountsAtTheThreshold() {
  post("/orders", cart("100.00"))
    .andExpect(jsonPath("$.discount")
      .value(10.00));
}
  • ✗ expected 10.00, got 0.00
  • ✗ gtaw: POLICY_ORACLE_MODIFIED, the edit is refused
  • re-ran twice: same result, not flaky
  • → reported as a defect, pinned with @KnownDefect
The bug is caught. A person decides what happens next.

The expected value comes from the spec a person confirmed, not from what the code returns today. A 2024 study of LLM-generated oracles found that they mostly restate the code’s actual behaviour (Konstantinou et al., arXiv:2410.21136). That finding is one reason this design exists. It is not a result measured on gta.

The loop

One command. Four agents. One referee.

Type /gta and the orchestrator asks gtaw what is next, then hands that job to one agent. The agents read code and write. gtaw runs every test and makes every decision an agent could get wrong. The picture below is a scripted replay of order.create, using the shape of gtaw’s real messages.

        —
        

          
The cast

          
Four agents do one job each. A program keeps the score.

          
Permissions are the fence. The agent that writes a test cannot declare that it passed, and it cannot change production code.

        

      

      

        

          
The one you talk to

          
gta-orchestrator

          
Takes /gta, asks gtaw for the next node, and hands it to the analyst, the author or the reviewer. Shows you gtaw’s status block, in English or Chinese. It does not write the spec or the test, and it never answers for you.

          
May run gtaw next, check, submit, answer, note, status. May not edit a file, run git, or decide that a test passed.

        

        

          
Reads the code

          
gta-analyst

          
Turns one flow into a behaviour spec: EARS requirements, scenarios, a diagram, and a question for anything uncertain. It describes. It does not decide that today’s behaviour is correct.

          
May write the named spec. May not write source=confirmed. That mark is yours, recorded by gtaw.

        

        

          
Writes one test

          
gta-test-author

          
Writes the test for one approved scenario. Expected values come from the spec. When the spec and the code do not settle how to write the test, it asks instead of guessing.

          
May edit the test files named in its brief. May not touch src/main, weaken a locked assertion, or skip the test.

        

        

          
Judges, and does not edit

          
gta-reviewer

          
Reads the test against the approved scenario. On a failure it picks one verdict: a product defect, a test defect, a spec error, or another cause from the brief. It never recommends changing the expected value to whatever the code returned.

          
Read only. One line back: verdict, and the reason.

        

      

      

        

          
The referee · not an agent

          
gtaw

          
A deterministic Java program. The same input produces the same decision. It has no mark on this page because it does not guess, and it calls no model.

        04
        

          
The bounds

          
What it will and will not do.

          
These are properties of the program, not a promise about a deployment we have not seen.

        

      

      

        

          
The run stays local

          
Tests run on the machine. Each run drops cloud credentials and the shell’s Spring profile and config variables, so a gta run does not load SIT, UAT or production configuration. Deployed environments are out of scope. The agents’ rules allow local dependencies only.

        

        

          
No containers required

          
Kafka and JMS run embedded. BigQuery and GCS use fakes. Oracle uses H2 in Oracle mode or a shared test schema. Pub/Sub uses an in-memory fake or an emulator downloaded from Nexus.

        

        

          
A test has to be able to fail

          
For a unit or slice test, gtaw can mutate the methods the spec cites (PIT) and send the test back if it still passes. If PIT cannot run, that is reported and not held against the test. The gate’s mutation mode defaults to advisory.

        

        

          
It asks. It does not guess.

          
Every question comes with one recommended answer and the reason. A bare OK takes it. OK, but … does not.

        

        

          
Your words are the record

          
Answers and approvals are stored as you wrote them, with the revision. A later reader can see who confirmed what.

        

        

          
English or Chinese

          
Set output.language to zh-CN and the questions and the status block are in Chinese. OK, 好 and 确认 all count as OK.

What you type

          
Eight ways in. One status block back.

          
Whenever gta stops for you, the block is gtaw’s: state, what happened, what was checked, what needs you, and what comes next. The orchestrator does not invent a second summary.

        

      

      

        
You typeWhat happens

        
          
/gtaContinue, or list the flows. OK works through all of them, riskiest first.

          
/gta order.createSpec, questions, your approval, then tests for that flow.

          
/gta explain order.createThe spec and the questions only. No tests.

          
/gta serviceEvery flow. One that is waiting for you does not stop the others.

          
/gta pr …The flows this branch changes. The PR description is the intended behaviour.

          
/gta incident order.create …A bug report becomes a test that fails on today’s code. You confirm the defect.

          
/gta note …Something the code does not say. Kept in .gta/notes.md.

          
/gta statusFlows, items, and what is waiting for you.

        
      

      
A bare OK takes the recommendation. OK, 2B changes one option. 好 and 确认 are OK. 批准 order.create@R2 approves that revision. 其余默认 keeps today’s behaviour for the remaining ordinary questions. Those scenarios become characterization tests: they lock what the code does now. They do not prove it is right.

Install

          
Build it once. Then the command is /gta.

          
From this repository the jar is the one you just built. A published jar also needs --distribution-url and --distribution-sha256. gtaw will not download an unpinned jar. The full notes are in the quickstart.

        

      

      
    
        
  1. 
          
    
            mvn -B install
            
    In this repository. Builds gtaw and runs its tests.
    
          
    
          
        
    2. 
        
  2. 
          
    
            java -jar toolkit/gta-cli/target/gta-cli.jar --root my-service init --platform copilot
            
    Once per service, usually by the person who owns the build. Use --platform opencode for OpenCode, then commit what init wrote. For a jar from Nexus, add the URL and the sha256 from the quickstart. For local development, GTA_CLI_JAR points gtaw at the jar you built.

  3.

    Checks the JDK, the build and the harness. On Windows: .\gtaw.cmd doctor.

  4.

        09
        

          
Questions

          
New to this? Start here.

        

      

      

        
Can it reach production?
It does not test deployed environments. Every run removes cloud credentials and the shell’s Spring profile and config variables, and the agents’ rules allow local dependencies only. SIT, UAT and production are out of scope.

        
Do I need Docker, or a separate model key?
Not for gtaw. Dependencies run embedded, as fakes, or — for Pub/Sub — with an emulator. The agents use the model your Copilot or OpenCode already provides. gtaw itself calls no model.

        
What if it is not sure?
It asks. The question includes the answer it recommends and why, so a bare OK is often enough. What the code cannot tell you, you can record once with /gta note.

        
What is a known defect?
A test that fails because the code is wrong, pinned with @KnownDefect. The build stays green and the defect stays visible. After the code is fixed, the test fails until the annotation is removed.

        
Is the goal coverage?
No. Coverage is reference only. gta checks that each approved scenario has a test, that a unit or slice test can fail, and that a new test is stable.

        
Which Java and Spring versions?
Spring Boot 2.2 to 4.1. Services on Java 8 and up. Maven or Gradle, one module or many, on Windows, macOS and Linux. gtaw itself needs JDK 17 or newer.
